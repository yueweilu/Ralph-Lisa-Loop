# Herdr 宿主管理的任务更新设计（2026-11-06）

> 实施状态（2026-11-09）：已在功能分支实现任务更新只读预检、正式意图/回执、混合代次链、Ralph Pane 请求适配器和协调器的一次性任务通知；本地宿主与假 Herdr 测试通过。真实 Herdr 聊天改任务、任务事件后的重启接续及故障注入矩阵尚未验收，不能据此宣称 D5 完成。

## 问题与目标

公开 CLI 的 `update-task` 能在 tmux 会话中追加任务方向。Herdr 领取宿主租约后，旧写入口被保护性拒绝；开发前插件没有等价入口。实测在 Ralph 窗格中提出新官网任务后，Ralph 的方案被提交并交给 Lisa，但正式 `task.md` 仍是 README 任务，Lisa 因此给出 `NEEDS_WORK`。

原 tmux 本身不解析聊天任务。原路径是 Ralph 接到新要求后调用 RLL 的 `update-task`，由命令追加 `task.md`；watcher 在后续轮次读取最新任务方向。Herdr 版保持这个用户动作和聊天入口，替换的是宿主租约期间被保护的正式写入口与交接协议。

目标是在**同一 Herdr 项目与两席 Pane**中保留原有使用体验：用户在 Ralph 聊天中明确提出新任务，Ralph 调用受控的宿主任务更新入口，让后续提交和 Lisa 评审使用新任务。Herdr 不擅自把任意终端文本解析为任务；由 Ralph 明确发起结构化更新请求。请求只能说明 Ralph 的判断，不能伪称插件已独立验证聊天内容的来源。

## 用户入口

**首要入口是 Ralph 聊天窗格。** Ralph 收到明确的任务变更要求后，读取当前正式任务，调用 Herdr 插件提供的受控请求命令并报告任务更新回执；若请求被阻断，明确展示原因，不继续以旧任务提交。原 tmux 模式由 Ralph 使用 `update-task` 的行为在 Herdr 中应对应这条路径，而不是要求用户切换到另一个窗格输入一遍。

请求分为：

1. **补充当前任务**：保留当前轮次与负责席位，追加明确的约束或纠正。
2. **切换新任务**：保留同一项目与 Pane，创建新的逻辑任务周期，由 Ralph 从规划开始；旧任务和候选保留为历史。

Ralph 应在聊天中回显旧任务、新任务、模式、目标席位与待失效候选。当前 Herdr API 未证实能独立识别用户聊天消息，因此事件记录必须标注任务内容由 Ralph 提交、来源未经插件独立验证。控制 Pane 可提供同一能力的人工备用入口和只读状态；它不是默认路径，也不宣称原生 GUI 按钮。

## CLI 契约

新增只读 `host task-update-check` 和写入 `host task-update`，请求中必须带项目规范路径、租约 ID、请求 UUID、预期代次、绑定代次、状态摘要、更新模式与正文 SHA-256。Ralph Pane 内的插件适配命令参照现有 `candidate-propose`，核对真实 Herdr Pane、Agent 身份和项目绑定，再把结构化请求交给持有租约的协调器；不向 Agent 暴露租约 ID。`task-update-check` 返回当前任务版本、待处理候选、阻断项和预期结果；不得写业务状态。插件另行核对自己的投递游标，CLI 不读取插件私有记录。写入命令必须重新检查所有前置条件，不能信任先前预检。

任务更新是独立的**宿主事件**，不能直接调用旧 `update-task`。原因：`task.md` 参与 `businessDigest`，当前 `generation` 和提交回执链要求业务摘要连续。事件要有写前意图、业务文件变更、持久回执、代次推进及崩溃后只读核对。原有 Agent 提交回执保持不可变；新事件按代次顺序加入同一状态转换链。旧会话没有任务更新事件时，按现有回执链解释，不迁移或重写旧回执。

每次任务更新保存：请求 UUID、任务版本、模式、正文摘要、更新前后业务摘要、前后轮次与席位、租约及绑定、时间、发起席位及 `source_verification=unverified`。正文在正式 `task.md` 中可读；记录不保存原生 Agent 会话 ID。相同请求 UUID 只返回已有回执；不同正文或预期状态复用 UUID 报冲突。2026-11-09 的产品决定允许**当前项目、当前会话**的明确自动提交授权：人工模式仍须逐份人类来源确认；授权模式的合格候选可自动提交，但回执必须标记 `session_authorized_auto`、`source_verification=unverified`，并保持其他门禁。切换新任务撤销该授权，补充当前任务可保留授权但后续候选重新过门禁。

## 状态与并发规则

- 写入前要求协调器正常运行、租约和两席绑定一致、当前回执已投递、无在途提交/控制/任务更新意图。任一条件不明时停止并提示核查。
- 在宿主锁内重新校验代次与摘要。先持久化意图，再变更 `task.md`、`history.md`、`last_action.txt` 和必要的轮次文件，最后持久化事件回执。每个可中断点都能由只读检查区分“未写入”“已完成”与“待人工核对”。
- 补充模式保持当前 `turn`、`round`、`step`。切换模式开启新的任务周期，`turn=ralph`、`round=1`、`step=planning`；历史任务与回执不删改。
- 更新前已提议但未正式提交的候选保留审计记录，标记为过期；它们的旧代次或摘要不能通过 `commit-check`。已确认来源但尚未提交的候选也不能跨任务版本提交。
- 如果更新时有已提交但尚未投递的回执，先完成或人工核对该回执；任务更新不得跳过交接。
- 旧 `update-task` 在宿主占用期间继续拒绝。非宿主 tmux 会话行为保持原样。

## 协调器投递

协调器从任务更新回执识别事件类型。补充模式把更新通知投递给当前负责席位；切换模式投递给 Ralph。提示包含项目、任务版本、回执 ID 和 `task.md` 路径，要求重读正式任务。事件投递先写意图，再调用 Herdr `agent prompt`，仅在匹配的 `agent_prompted` 回执后推进游标。重启、重绑和接续检查须核对任务更新投递；结果不明时禁止自动重发。

Lisa 后续正常交接仍按最新正式任务评审。任务更新事件本身不会确认或提交任何 Agent 候选；人工模式的来源确认门禁不变，自动模式只使用单独持久化的会话授权，不能伪造人审记录。

## 验收顺序

1. CLI 单测：同一会话从 README 切到官网；摘要与事件链连续，旧候选失效，自动授权撤销后的新候选回到来源确认门禁。
2. 故障注入：写前、写中、回执后、投递前后中断；重复请求幂等，不确定状态只读核对。
3. 插件测试：真实 CLI + 假 Herdr，验证 Ralph Pane 发起、错误席位拒绝、当前席位通知一次、暂停和未投递回执阻断；控制 Pane 仅作为备用入口。
4. 隔离真实 Herdr：新建临时项目和命名 Server，双席原生会话就绪后中途切换任务；核对 Ralph 规划、Lisa 按新任务评审及重启后不重投。
5. 回归：原 tmux `update-task`、旧回执会话、S4 重启接续、S5 安装/更新和 Node 18/20/22 CI。

当前演示会话已有未提交的 Lisa 候选，不作为新协议的首次写入对象；先在隔离会话验收，再判断其升级路径。不得热替换正在运行的协调器。

## 当前实现与使用边界（2026-11-09）

Ralph 在自己的 Herdr Pane 收到明确的补充或新任务时，把要求写成项目内的 UTF-8 文本文件，调用插件 checkout 中的 `task-update-request.mjs request --project <绝对项目路径> --file <绝对文本路径> --mode supplement|switch --request-id <新 UUID>`。适配器核对当前 Pane、Ralph/Claude、项目和席位绑定，只排队请求，不打印租约 ID，不直接修改业务文件。协调器核对自身投递游标后，使用 `host task-update-check` 和 `host task-update` 正式提交；`host receipt` 可只读查询同一请求 ID。Ralph 必须等正式回执及协调器通知后再提交新候选。插件没有聊天文本解析器或新增 GUI 按钮。

`switch` 将负责席位重置为 Ralph、轮次重置为 1、步骤重置为 planning；`supplement` 保留现有席位、轮次和步骤。两者均推进代次及任务版本，旧候选因代次不符不能提交。当前实现对两种更新都保守地结束旧自动提交授权；后续候选按人工来源确认门禁处理，直到有独立的新任务授权流程。原 tmux `update-task` 没有修改。

本地覆盖了只读预检、同请求幂等、切换与补充、混合事件后继续正式提交、旧候选拒绝、错误席位拒绝、Lisa 负责时 Ralph 请求切换、一次通知和授权失效。请求队列采用先写临时文件再原子更名；未处理请求阻止停止与租约回收。任务写入或投递结果不明时保留意图并阻断自动重试。

对写前中断的任务意图，`host receipt --request-id` 现在只读返回 `audit_status`、业务摘要及未匹配的固定文件名；不会重放写入，也不输出任务正文。写中和回执后故障矩阵及真实 Herdr 重启接续仍待执行。

任务更新投递确认后，协调器现在立即归档对应请求。若进程恰好在游标已前进、请求尚未归档之间退出，租约恢复仍会被待处理队列阻断。先只读核对 `host snapshot`、`host receipt --request-id`、插件 `record.json` 和 `delivery-<request-id>.json`；四者显示同一代次、同一回执且投递状态为 `accepted` 时，才可在原隔离插件环境执行 `node integrations/herdr/coordinator.mjs archive-delivered-task-request <request-id> <generation-after>`。此命令只归档该请求，不投递 Agent 提示，也不推进业务代次；证据不匹配时返回错误并保留请求。随后重新执行既有的 `recovery-check`、显式租约回收、重绑与接续。未正式提交、未确认投递或部分写入的请求不适用此命令，仍须人工核对，不得用删除队列文件的方式跳过门禁。本地回归覆盖了这一已投递中断窗口；真实 Herdr 重启验收仍待执行。

真实测试还发现 Claude 执行受权限审批的 Bash 时，Herdr 可能将其标为 `blocked`；Pane 适配器现在只在有匹配原生 Claude 会话、交互就绪、当前 Pane/终端/项目均相符时接受该状态。`idle` 和错误席位仍拒绝。协调器若遇到 Ralph 正在完成发起请求的聊天轮次，会等待其 `idle/done`，不把 `AGENT_NOT_READY` 当成需要回收租约的故障。与原生会话有关的检查是席位连续性证据，不是候选作者证明。

若协调器在**任务写入前**退出，`host receipt` 为 `unknown`、快照保持请求的原代次与摘要、插件游标未前进且没有投递文件时，可在确认插件记录为 `needs_reconcile` 后执行 `node integrations/herdr/coordinator.mjs abandon-uncommitted-task-request <request-id> <generation-before> reviewed-no-commit`。命令再次只读核对以上事实，再把请求移入 `task-update-requests-abandoned` 审计目录；不删除正文、改业务状态或投递提示。任何意图、正式回执、摘要变化或未确认投递都会阻断。现场按这条路径处理一次后，显式回收旧租约、重绑并接续，旧提示没有重放。参见[现场记录](d5-chat-task-update-live-2026-11-09.md)。

本地故障形态回归现在构造有效的任务更新意图，分别核对写前 `before`、所有业务文件已写入的 `applied`、部分业务文件被改动的 `partial`，以及 `turn.txt` 无效导致常规项目检查失败的情况。后一种情况仍返回受限的任务意图核对字段、`state_digest_observed=null` 与未匹配文件名，而非丢失证据；不输出任务正文。这是合成故障状态的只读测试，不等于真实进程在每个文件写入点被终止后的端到端验收。
