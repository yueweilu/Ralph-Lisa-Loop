# Ralph-Lisa Herdr plugin (S3.6/S4.2 preview)

This is the public-repository Herdr plugin, separate from the Claude Code plugin in `plugin/`. It needs Herdr 0.9.4 or later, Node.js 18 or later, and a Ralph-Lisa CLI with the S1 host commands.

## Current behavior

- `doctor` checks Herdr version, the Ralph-Lisa host contract, Claude/Codex Herdr integrations, and both agent CLI login states. It reports one JSON object with a setup code and individual checks.
- `status` reads one project's RLL snapshot. It takes the project from `settings.json` or the invoking Herdr workspace. It does not claim a host lease or change RLL state.
- `seat-preflight` verifies two existing Herdr agents named `ralph` (Claude) and `lisa` (Codex), their live Terminal/Pane/Workspace IDs, readiness, project path, and any native Agent session references, then returns a proposed RLL binding without claiming a lease or writing a binding. Only SHA-256 fingerprints of native references enter the plan; a seat without a reference remains explicitly unrecorded.
- The `control` pane shows these read-only views and can refresh them.
- The `review` pane lists immutable candidate metadata, displays the selected candidate's complete stored body with line numbers and visible escapes for terminal controls, identity and SHA-256, and runs `host commit-check`. It requires a person to type `COMMIT <candidate-id> <full-sha256>` before calling the existing `confirm-candidate` and `commit` commands. A policy block or changed candidate stops before confirmation; an uncertain commit result requires `host receipt` inspection with the displayed request ID. This is an explicit human source assertion, not proof of file authorship or unattended delivery.
- `start` writes an exclusive local intent. If both `ralph` (Claude) and `lisa` (Codex) are already ready in the invoking workspace, it attaches to them. If neither exists, it creates a dedicated Herdr workspace, splits two panes, starts both agents, waits for interactive readiness, and rechecks their returned IDs. It then claims the RLL host lease, binds the seats, and prepares generation zero. After validating the initial Ralph turn and project task file, it writes an initial delivery intent and prompts Ralph once to read the task. Only a matching Herdr `agent_prompted` acknowledgment permits `started`; an uncertain result stays in `needs_reconcile` without replay. Later starts for the same RLL session do not repeat the initial prompt. The coordinator heartbeats every five seconds.
- After binding, the coordinator prepares RLL generation zero. It polls the validated RLL snapshot and looks up each new committed receipt through `host receipt`. Only a receipt for the current lease, binding, session, generation, and expected role may trigger a prompt to the opposite verified Herdr Agent. A durable delivery intent is written before `agent prompt`; only Herdr's `agent_prompted` response with the expected Agent kind, name, project, Workspace, and Pane advances the local cursor. A gap, identity change, ambiguous prompt result, or existing generation without recovery stops in `needs_reconcile` without automatic replay. This preview has no automatic recovery of a stopped coordinator.
- A native Agent session reference can appear after Herdr accepts the first prompt. Each heartbeat rechecks the same prompted Agent in its bound Pane and Terminal; when Herdr first exposes a valid reference, the coordinator durably saves only its SHA-256 fingerprint for later S4 continuity checks. This does not add a prompt or infer candidate authorship. An unprompted Lisa remains explicitly unrecorded.
- Every five seconds the active coordinator also checks that both bound Herdr Agents still occupy their recorded Terminals before heartbeating the RLL lease. Loss of the Herdr API, an unavailable Agent, or a changed Terminal stops the coordinator in `needs_reconcile` while retaining the lease for review. This fences a plugin action process that may survive a Herdr Server restart. The next prompt checks the Terminal again before delivery; this does not provide automatic lease takeover.
- A blocked Agent startup emits `needs_input` with its workspace and pane ID while the coordinator waits up to two minutes for a person to handle the prompt. It does not accept trust, permission, login, or update prompts on the user's behalf. A partially existing or mismatched named seat fails closed. `stop` currently applies only after the lease becomes active. After a preclaim timeout or managed Pane close, inspect the retained plugin record and Herdr panes. The same launch request can retry only through the existing preclaim seat and state checks; the earlier launch result is archived before the current result is replaced. Uncertain delivery or a claimed lease still requires explicit review.
- For a managed launch, closing the coordinator Pane while it waits for an Agent before claiming the lease records `MANAGED_PANE_CLOSED_DURING_START` and stops that wait. The partial seat and preclaim record remain for inspection; the process does not delete the project or silently restart the Agent. Once active with no pending receipt, SIGTERM, SIGINT, or SIGHUP wakes the coordinator immediately to check the cursor and release the lease. If the snapshot is busy or changed, the lease remains claimed for explicit recovery. A close signal queued during synchronous claim, binding, or generation preparation is checked before the initial prompt intent: the coordinator stops without prompting Ralph and retains the claimed lease in `needs_reconcile` for explicit recovery. If closure overlaps the actual prompt command, inspect its durable delivery intent and Herdr receipt before any recovery; the result may be uncertain. [The isolated P2 close trial](../../docs/herdr/p2-live-managed-close-2026-11-09.md) records the real Herdr 0.9.4 close behavior and its remaining native-session limitation.
- `pause` writes a request and waits for the active coordinator to acknowledge `paused`; automatic prompts then halt while lease heartbeats continue. A submitted receipt that arrives while paused stays pending. `resume` requires the exact RLL state seen at pause time, no unhandled receipt, and both original Agents ready in their bound panes. If an Agent is still working, the action returns `AGENT_NOT_READY` and remains paused so it can be retried. A changed RLL generation or seat identity stops in `needs_reconcile` rather than guessing whether a manual prompt was already sent.
- `stop` sends a durable request to an active or paused coordinator and waits for the RLL lease release when no receipt is pending. For `rebound_paused`, no coordinator is running; `stop` verifies the unchanged cursor and releases the replacement lease directly. It leaves Claude and Codex running. The released binding becomes stale. The Herdr action log, rather than the initial invocation response, confirms completion.
- `recovery-check` is read-only. It asks the public CLI for a lease recovery evidence hash, checks the plugin record and initial/handoff delivery intents against the saved seat plan and current CLI binding, and observes whether the named Herdr Agents still match the saved Workspace and Pane. It rechecks the CLI evidence and plugin records after observing both seats; a change during the audit returns `RECOVERY_STATE_CHANGED` and requires a fresh check. It reports a point-in-time `coordinator_process` observation and `continuation_blockers` for a present/unknown PID, uncertain or missing delivery records, cursor mismatch, pending control request, missing plugin record, or a seat that needs rebind. A PID may have been reused; absence does not prove no prompt is in flight. For each seat it reports whether Herdr currently exposes a native Agent session reference and whether its SHA-256 fingerprint matches the one saved by the coordinator. `manual_rebind_required` means at least one seat is missing, changed, or has no matching saved reference. Older records without a saved reference remain unverified. Changed business state or mismatched binding/delivery identity returns `needs_reconcile`. The reads are sequential, not an atomic snapshot. An empty blocker list is not permission to recover a lease or resume delivery; human review remains required.
- `rebind-check` is a separate read-only preflight after a person has run the CLI's explicit `host recover-lease`. It requires the archived old lease and matching recovery receipt, no current lease, an exited old coordinator, a complete accepted delivery chain across nested prior-lease archives, a cursor matching the RLL generation, and two ready Herdr seats. Every previously prompted Agent must retain its recorded native session fingerprint; an unprompted Lisa may be started in a new session. It returns the proposed new binding and evidence digest for review. It never claims a lease, rebinds a seat, or prompts an Agent. A matching result is not an authorization to continue automatically.
- The `rebind` Pane shows that plan and requires the exact `REBIND <evidence-sha256>` text. The guarded coordinator entrypoint reruns the preflight, claims a replacement RLL lease, verifies and binds both live Herdr seats, archives the previous plugin record and accepted delivery chain, and records the current generation as `rebound_paused`. It sends no Agent prompt. If any step after the durable rebind intent fails, the marker remains and subsequent recovery checks require manual reconciliation. A normal `start` still finds the archived initial prompt and cannot replay it after the replacement lease is stopped.
- `continuation-check` is a read-only gate for `rebound_paused`. It verifies the replacement host lease against its durable record, the archived accepted delivery chain and saved cursor against the current RLL snapshot, pending plugin controls, and both ready Herdr seats. A previously prompted Agent must retain its native session fingerprint. It rereads the host and plugin state after observing the seats and returns an evidence SHA-256 only when no blocker remains. This check does not start a coordinator, heartbeat, or prompt; its result can become stale immediately.
- The `continue` Pane requires the exact `CONTINUE <evidence-sha256>` text. The coordinator reruns `continuation-check`, records an exclusive continuation intent, checks the saved cursor and both Terminals again, heartbeats the replacement lease, then starts the shared receipt-driven loop without replaying any historical prompt. A changed seat or uncertain write retains a manual-review marker. New receipts must belong to the replacement lease and advance the saved cursor by one; one durable intent is written before each Herdr prompt. The normal `resume` action does not start a `rebound_paused` coordinator.
- Automatic candidate submission is not implemented. The current CLI source gate requires a human to review and confirm each candidate before `host commit`, so this preview does not deliver an unattended Ralph/Lisa loop.
- `candidate-propose.mjs` is an optional Agent-pane helper for the current manual gate. It asks Herdr for the calling Pane (`pane current --current`) and its live Agent, checks the RLL seat binding and current turn, then calls the existing `host propose`. It returns the observed Pane/Terminal and immutable candidate digest, while keeping `source_verification=unverified` and `commit_ready=false`. A plugin action's focused Pane context is not a caller identity; do not use it to authorize an automatic commit.

`ready` means the read-only preflight passed at that moment. Claude/Codex can be detected from their terminal screens without Herdr integrations. The `integrations` checks remain visible because they are needed to resume the same Agent sessions after a Herdr server restart. `started` means the host lease, bindings, generation baseline, and initial Ralph prompt are accepted; `handed_off` is emitted only after Herdr accepts a receipt-driven prompt. `status` includes the plugin coordinator phase and initial prompt status when a local record exists. RLL still labels seat verification `unverified`, because its CLI does not independently authenticate Herdr's returned IDs.

## One-command task launch (preview)

From a built checkout, run `node cli/dist/cli.js auto --host herdr --project /absolute/project "TASK"`, or the equivalent `node cli/dist/herdr-rll.js --project /absolute/project "TASK"`. An installed CLI also exposes `herdr-rll`. Launching records one immutable request for a new RLL session, opens the project Workspace and managed coordinator Pane, and reports its launch result. It refuses to overwrite an existing RLL session. The `--full-auto` flag only selects the Agent permission profile; candidate submission still requires the existing human source confirmation. For Codex CLI 0.167.0, the plugin uses `--no-daemon --sandbox workspace-write --ask-for-approval never`; this avoids an unsupported `--full-auto` Codex argument while keeping Codex commands inside its workspace-write sandbox. Execution failures return to Codex without an approval prompt.

Inside Herdr, first focus the intended project Workspace, then open the plugin's **Start Ralph-Lisa task** overlay. Herdr 0.9.4 attaches overlays to the currently active Pane; `--workspace` and `--target-pane` cannot direct this overlay. The input page shows the canonical project and whether an RLL session already exists, then asks for the task, the Agent permission profile (`interactive` by default or `full-auto`), and a final start confirmation. It shows a short task preview and explicitly states that formal candidate commits still need separate source confirmation. Canceling before the final confirmation does not initialize a session. The managed coordinator opens in the same project Workspace after launch.

If launch output is interrupted or a Pane remains open, use `herdr-rll status --project /absolute/project` (or `node cli/dist/herdr-rll.js status ...`) before taking further action. This command reads the saved request, launch receipt, and current RLL host snapshot; it does not start or resume Agents. `pending` means there is no saved launch result, `needs_input` means the startup reported a user prompt, and `needs_review` means a saved `started` result no longer matches the current host binding. `claimed_unverified` means the saved `started` result matches a claimed binding at read time; it does not prove that the Herdr Server, Agent panes, or coordinator process are still running. A snapshot error returns `needs_reconcile` with a code for inspection. Do not repeat the launch command to recover an uncertain result.

## GitHub installation

Install this repository's `integrations/herdr` subdirectory through Herdr's `plugin install` command. Herdr runs the manifest's build commands before registration: `npm ci` in the sibling `cli/` package, TypeScript build, then the package-content check. The plugin chooses that same checkout's built `cli/dist/cli.js` when no CLI override is configured. Installation fails if the source checkout does not include the sibling CLI or the build/check fails. An [isolated Herdr 0.9.4 trial](../../docs/herdr/s5-real-github-install-2026-11-05.md) verified installation at commit `8d6f933`, same-checkout CLI, `doctor`, uninstall, and config preservation. A later [branch-ref update trial](../../docs/herdr/s5-cross-commit-update-acceptance-2026-11-05.md) moved the installed plugin from `f66ce12` (`0.1.0`) to `6c3a672` (`0.1.1`) while preserving config and passing `doctor`. A [GitHub-installed dual-Agent trial](../../docs/herdr/s5-github-dual-agent-closure-2026-11-06.md) verified one confirmed commit and one handoff in each direction. A later [v0.1.2 fixed-commit trial](../../docs/herdr/s5-v012-live-retry-and-dual-handoff-2026-11-06.md) verified the same two handoffs and the new first-start retry in an isolated named Server.

The CLI now waits briefly for a competing short command lock before a `host commit` begins. A persistent `HOST_BUSY` still requires receipt and lock inspection without blind replay. This [contention mitigation](../../docs/herdr/s5-commit-lock-contention-2026-11-06.md) has passed local tests but has not yet been rechecked in a managed Herdr trial.

## Local setup

Build the public CLI first (`cd cli && npm ci && npm run build`). Herdr does not run manifest build commands for a local `plugin link`. The npm release `ralph-lisa-loop@0.3.13` did not contain `host` when checked on 2026-11-05. From this checkout, link the plugin:

```sh
herdr plugin link /absolute/path/to/Ralph-Lisa-Loop-herdr/integrations/herdr
herdr plugin config-dir ralph-lisa.loop
```

The second command prints the per-plugin config directory. An optional `settings.json` there can pin an absolute project and CLI argv:

```json
{
  "project": "/absolute/path/to/your/project",
  "rll_cli_argv": ["node", "/absolute/path/to/Ralph-Lisa-Loop-herdr/cli/dist/cli.js"]
}
```

Without `project`, a Herdr workspace action uses the absolute `workspace_cwd` from `HERDR_PLUGIN_CONTEXT_JSON`, checking it against `HERDR_WORKSPACE_ID` when both are provided. Without `rll_cli_argv`, a source checkout uses its sibling `cli/dist/cli.js`; if it is unbuilt, it fails instead of falling back to a potentially stale global CLI. Initial and handoff prompts give Agents that same checkout's exact CLI command for host checks. A standalone plugin directory without sibling CLI source resolves `ralph-lisa` on `PATH`. An explicit `rll_cli_argv` overrides either default; in that case prompts refer to the configured CLI without displaying its arguments. The project must already be initialized for `status` to return a snapshot. `settings.json` must be a regular file; malformed values return `INVALID_SETTINGS`.

Then run `herdr plugin action invoke ralph-lisa.loop.doctor`, inspect `herdr plugin log list --plugin ralph-lisa.loop`, and open the read-only pane with `herdr plugin pane open --plugin ralph-lisa.loop --entrypoint control --placement tab` from a Herdr workspace. Action invocation is asynchronous; the command log carries the result. `herdr plugin unlink ralph-lisa.loop` unregisters the local link.

For the S3 trial, initialize a disposable RLL project, open it as a Herdr workspace, and invoke `ralph-lisa.loop.start`. When it creates a dedicated workspace, handle any Agent startup prompts in the reported panes. If startup stops before claiming a lease or writing an initial prompt intent, the same action may retry only after checking the recorded error and resolving the Pane prompt. The retry checks the original Workspace, Pane and terminal IDs, project path, live Agent identities, unchanged RLL session and digest, and absence of other state files; uncertainty still requires manual review. Older failed records without terminal IDs cannot use this retry. Check the action log for `initial_prompted` and `started`; Ralph should receive one prompt to read `.dual-agent/task.md`. Use this checkout's built CLI (`node <checkout>/cli/dist/cli.js host snapshot --project <abs> --json`) to confirm the claimed lease, two bound seats, and `generation=0`. Review a Ralph candidate, run the CLI's `commit-check` and `confirm-candidate` gate, then `host commit`; expect one `handed_off` log and one prompt in Lisa's pane. Repeat with a Lisa `NEEDS_WORK` candidate and expect one prompt in Ralph's pane. Invoke `ralph-lisa.loop.stop` from the project workspace; confirm both action logs succeeded and the snapshot reports `host_state=unclaimed` and `binding_state=stale`. The two Agents remain running. Do not run this trial against a live tmux or manually managed session.

To make a seat-checked proposal from a working Agent's own Herdr pane, run `node <installed-plugin-root>/candidate-propose.mjs propose --project <absolute-project> --file <project-relative-candidate-file> --candidate-id <uuid>`. Run it as an Agent tool command, not from another focused Pane or the plugin control action. It reads the plugin's CLI setting through `herdr plugin config-dir ralph-lisa.loop`. A successful proposal still requires a person to review the candidate and call `host confirm-candidate` before `host commit`; the helper does not prove which process wrote the file.

If this helper returns `CALLER_AGENT_NOT_WORKING`, the result includes Herdr `agent get`'s observed state and no candidate was saved. A short bounded recheck only handles a just-dismissed `blocked` UI; it still requires a real `working` observation. Inspect the actual Agent pane and current state before retrying; `blocked`, `idle`, `done`, and `unknown` never pass the proposal gate. `CALLER_AGENT_MISMATCH` means the project, Pane, Workspace, or Terminal identity failed to match.

Open the plugin's `review` pane in the project workspace, select the candidate ID, read its full body and Herdr seat binding, then type the displayed exact confirmation string if you accept its source and want to submit it. The Pane creates one request ID and prints it before any write. An empty response cancels; a prior candidate from another turn fails `commit-check`. If submission becomes uncertain, inspect `ralph-lisa host receipt --project <abs> --request-id <displayed-id> --json` before taking any further action. The Pane never retries a write automatically.

For manual intervention, invoke `ralph-lisa.loop.pause` and wait for its `paused` result before typing in either Agent Pane. `status` then shows `coordination.phase=paused`. When both Agents are ready and the RLL state is unchanged, invoke `ralph-lisa.loop.resume` and wait for `active`. If you submitted a candidate while paused, `resume` requires reconciliation and does not send a possibly duplicate handoff.

If the coordinator or Herdr server crashes, the RLL lease remains claimed. Do not delete the lease or rerun `start` blindly. Inspect the plugin state directory and `ralph-lisa host recovery-check --project <abs> --json`; recover only after checking that the old coordinator and agents are stopped and no submission is in flight. The plugin has no automatic lease takeover.

Invoke `ralph-lisa.loop.recovery-check` from the project Workspace to see the CLI lease evidence, plugin delivery states, and live seat observations together. The action does not call `host recover-lease`; inspect the recorded `required_checks` and actual panes before using the CLI's explicit recovery command.

After an explicit, reviewed lease recovery, invoke `ralph-lisa.loop.rebind-check` from the project Workspace once the two Herdr Agents are ready. Inspect `continuation_blockers` and the proposed binding. Open the plugin `rebind` Pane in that Workspace and type its exact confirmation string to claim and bind a replacement lease in `rebound_paused`. Inspect `host snapshot` and the Pane result; do not retry an uncertain write. `ralph-lisa.loop.stop` can release this paused replacement lease. Normal `resume` does not yet continue it or deliver a new receipt.

After rebind, run `ralph-lisa.loop.continuation-check`. Review the returned lease, generation, turn, seats, and blockers. Open the plugin `continue` Pane in the same Workspace and type its exact confirmation string. The Pane must report `continued` before the coordinator is considered active. It sends no prompt on startup; later committed receipts drive handoffs. If the result is uncertain, inspect the RLL snapshot, plugin record, and `continuation.pending.json` before any further action. The real nonzero-cursor Server restart and repeated rebind path was accepted in an isolated named Herdr session; see the [live continuation record](../../docs/herdr/s4-live-nonzero-continuation-2026-11-05.md) for the observed runtime limitation.

In one isolated Herdr 0.9.4 restart trial, Ralph's Claude session reference survived and the same named Agent resumed; Lisa had no native Codex session reference before restart and returned as an empty Pane. In a later trial, the plugin action coordinator survived Server shutdown as an orphan and kept heartbeating the claimed RLL lease, despite Lisa being unavailable. Its explicit `stop` action released the lease. The active coordinator now checks both Herdr Agents and their Terminal identities before each heartbeat. A fresh real restart trial with the updated code confirmed that the old coordinator exited, its record changed to `needs_reconcile`, and the RLL lease remained claimed without further heartbeats. See the [first restart trial](../../docs/herdr/s4-real-restart-2026-11-04.md), [native session binding](../../docs/herdr/s4-native-session-binding-2026-11-04.md), and [orphan coordinator fence](../../docs/herdr/s4-server-epoch-fence-2026-11-04.md). A later isolated trial used both real native sessions and accepted two nonzero-cursor restarts, repeated explicit rebind, and one Lisa-to-Ralph handoff; its [record](../../docs/herdr/s4-live-nonzero-continuation-2026-11-05.md) also preserves a subsequent `ACTIVE_SNAPSHOT_MISMATCH` requiring another reviewed recovery.

Herdr plugin installation and enabled state are global for the current user across Herdr sessions that use the same Herdr user directories. `HERDR_CONFIG_PATH` only changes the config file path; it does **not** isolate the plugin registry. For a disposable registration check on macOS with Herdr 0.9.4, setting **both** `XDG_CONFIG_HOME` and `XDG_STATE_HOME` to a temporary directory was verified to isolate the linked plugin from the normal Herdr plugin list:

```sh
HERDR_TEST_ROOT="$(mktemp -d)"
XDG_CONFIG_HOME="$HERDR_TEST_ROOT" XDG_STATE_HOME="$HERDR_TEST_ROOT" \
  herdr plugin link /absolute/path/to/Ralph-Lisa-Loop-herdr/integrations/herdr
XDG_CONFIG_HOME="$HERDR_TEST_ROOT" XDG_STATE_HOME="$HERDR_TEST_ROOT" \
  herdr plugin list --json
```

Keep the same two variables on the Herdr test server and subsequent CLI calls. `plugin link` validates the manifest without a running server; listing/invoking actions and opening panes need a running server. Do not infer that linking alone executed `doctor` or started Agents.
